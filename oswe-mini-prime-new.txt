User: # Refactor & Extend: LRU-Centric Train Data Request and Parsing System (MVB/PHM) — High-Performance, Modular, Concurrent, and Fault-Tolerant

This system migrates a mini-program to the web. The backend exposes multiple POST endpoints to request train data for MVB and PHM modules. Different modules are implemented by different interface files (Views). Request types (plot, download, parse) are served by distinct parsing functions inside their respective Views. The request body includes a configuration file (for parsing), a time window and step, carriage and train numbers, and the data type (MVB/PHM). Parsing starts from machine/byte code using client-provided logic; after primary parsing, a secondary pass computes metrics or transforms data for plotting or export. Previously, an LRU cache was added to improve performance, but incorrect cache hits and shared pollution occurred.

---

## 1. Current Issues (LRU at the center, systemic gaps acknowledged)

### 1.1 Caching & Consistency
- Incomplete cache keys: keys lack semantic dimensions such as `module/endpointId/requestType/configVersion/timeWindow/timeStep/carriage/trainNo/parseMode`, causing cross-request mis-hits and polluted results.
- Shared cache namespace: results from different interface files (Views) or modules pollute each other; both hit rate and correctness degrade.
- Missing TTL/expiration: old caches survive configuration or data upgrades, producing outdated results.
- Concurrency hazards: under load, identical keys are computed multiple times or overwritten; missing atomic writes and read/write locks.
- Cold-start thrashing: initial large-window requests cause burst evictions; hot-path results are frequently dropped.
- No caching of intermediate artifacts: secondary computations (plot metrics/aggregations) re-run repeatedly, wasting CPU and I/O.

### 1.2 Architecture & Maintainability
- Tight coupling among parsing, view rendering, and data sources (MinIO/DB). Clear layering and dispatch strategies are lacking.
- Hard-coded routing: mapping `module + requestType` to a specific View is scattered and difficult to evolve.
- Configuration loading is fragmented: no unified versioning and schema validation; rollback is fragile.

### 1.3 Performance & Reliability
- MinIO downloads are not parallelized and omit range reads; large time windows are slow.
- Parsing is not streaming/chunked; memory peaks are high.
- Plotting renders full datasets without downsampling/LOD; interactivity suffers.
- Logging/metrics are insufficient: hit/miss/eviction reasons and hot-key distribution are opaque; errors lack structured categorization.

---

## 2. Required Improvements (LRU and parsing pipeline)

### 2.1 LRU Redesign
- Structured keys: namespaced, semantically rich keys including `module/endpointId/requestType/configVersion/timeStart/timeEnd/timeStep/trainNo/carriage/parseMode`. Note: `endpointId` is resolved by server-side routing; do not place `view` in the request body.
- Tiered caching: in-memory LRU for hot keys + optional disk cache for colder data, each with configurable capacity and TTL.
- Concurrency safety: atomic writes, read/write locks, and request coalescing (identical keys compute once, other calls await the same future).
- Intermediate caching: store primary parsing outputs (domain-mapped signals) and reusable secondary metrics to avoid recomputation.
- Prewarming & ops: management endpoints to prewarm, clear, and inspect caches by module/interface file (View).
- Metrics & logs: hit/miss/eviction reasons, top-N hot keys, per-namespace hit rates, error taxonomy.

### 2.2 Data Pipeline & Parallelism
- Parallelized MinIO/DB fetch: slice the time window into segments and download in parallel; use range reads and resume on failures.
- Streaming/chunked parsing: pipeline processing to lower memory peaks; minimize copying and allocations.
- Shared secondary results: allow metrics/aggregations computed once to be reused across compatible endpoints.

### 2.3 API & Job Model
- Asynchronous jobs: `POST /jobs/parse` returns `jobId`; `GET /jobs/{id}` returns status/progress; `DELETE /jobs/{id}` cancels.
- Unified response envelopes: `{ requestId, status, data, error }` with retryable/non-retryable error codes.
- Time window conventions: ISO 8601, unified timezone, half-open intervals; endpoint selection driven by routing/URL (View is an interface file, not a request field).
- Versioned configurations: `/configs/{version}`; parsing endpoints accept explicit versions; support negotiation and rollback guidance.

### 2.4 Suggested Modular Layout
```
data_pipeline/
  __init__.py
  sources/            # MinIO/DB adapters
  parsers/            # bytecode → domain mapping, split by MVB/PHM
  views/              # interface files for plot/download/parse
  cache/
    __init__.py
    lru.py            # namespaces, structured keys, concurrency, metrics
  config/
  validators/
  routing/
  logging_utils.py
  metrics.py
  errors.py
  plugins.py
compat/               # compatibility layer preserving legacy APIs
```

### 2.5 New Features
- Configurable caching policies (capacity/TTL/namespaces/tiered storage).
- Snapshot/clone support for consistent concurrent reads (MVCC-like).
- Unified empty/loading/error states for Views.
- Parallel filtering and downsampling to improve interactive performance.

### 2.6 API Compatibility
- Preserve existing semantics (multiple POST endpoints, View-based dispatch) while introducing a compatibility layer bridging old and new.
